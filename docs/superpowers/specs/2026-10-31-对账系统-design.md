# 对账系统设计（financial-bill-project）

> 日期：2026-10-31 · 状态：待批准
> 需求来源：《一文搞懂「对账系统」》（陈天宇宙，全文与 76 张原型图存档于 `docs/reference/`）
> 本文中标注【决定】的条目是建造者的决定，不是用户确认过的内容；未标注的条目是用户明确要求的。

## 1. 意图与背景

用一套自动化系统替代人工对账：把**自有支付/交易记录**与**渠道（微信/支付宝等）清算、结算文件**按规则逐笔/汇总核对，产出对平、单边、错账等结果，并对差异（差错）进行登记、处理、核销，保证"账、证、实"一致、可追溯。

背景依据（来自文章）：人工逐笔核对慢且易错；对账必须可配置（业务会变）；对账引擎必须可控（连续性、状态、任务流）；差异必须闭环（发现→排查→处理→核销）。

## 2. 目标 / 非目标 / 反目标

**目标（一期必须达成）**
- 渠道清算/结算文件与自有支付记录均可通过**文件上传**（Excel/CSV/TXT）进入系统，解析规则可配置（文件列 → 标准字段映射）
- 三种核对模型落地，分三期交付：一期**交易对账**（逐笔）；二期**资金对账**（费用项汇总、长短款）+ **余额调节对账**（在途/未达账）；三期**自动获取**（渠道文件接口/SFTP/SQL）+ 记账推送与告警对接
- 对账引擎：按"日 × 对账项目 × 逐笔"执行，产出对平/单边/错账；结果独立存储（同一份数据可参与多个对账项目）
- 差错处理：差异登记、按可配置的差错处理类型（SOP）处理、留痕；二期增加长短款挂账与核销
- 结果查看：对账结果总览（项目 × 日期：总笔数/单边/错账/待处理）+ 明细下钻（A/B 两方数据并排）
- 多并发安全：对账执行为异步任务（队列 + 多 worker），不阻塞 Web；同一项目同一日不会被并发执行两次；重对幂等
- docker compose 一键起全栈（开发可用，实体机可直接部署）；git 按阶段管理

**非目标（一期明确不做）**
- 不做自动获取渠道文件（接口下载/SFTP/SQL 捞取）——三期
- 不做账务系统对接（金蝶等记账推送）——三期
- 不做跨日自动轧差（时间差差异不自动对平，挂起人工确认）
- 不做一对多/多对多的复杂匹配模式（一期只支持 1v1，以及"B 方同键多行汇总后比 1 行 A"的单向汇总）
- 不做多租户
- 不做移动端

**反目标（做了就算失败的）**
- 对账结果不可追溯到具体源数据行（必须能点开看到 A 行原文和 B 行原文）
- 同一对账日重复执行产生重复差异记录（必须幂等）
- 上传一个坏文件（列缺失/编码错误）导致解析任务挂死或污染已入库数据（解析失败必须整批回滚并明确报错到行号）

## 4. 技术选型【决定】

| 项 | 选择 | 理由（一句话） |
|---|---|---|
| Python | 3.11（`python:3.11-slim` 镜像） | 稳定、Django 5.x 支持良好、实体机无兼容问题 |

| 数据库 | PostgreSQL 16 | 并发安全、JSON 字段、部分唯一索引；实体机跑一个容器足够 |
| 异步任务 | Celery + Redis 7 | 用户要求多并发：队列解耦、worker 可横向加、任务可重试；单机部署成本可接受 |
| 文件解析 | openpyxl（xlsx）、标准库 csv、自写 TXT 分隔符解析 | 覆盖文章提到的 Excel/CSV/TXT 主流格式 |
| 文件存储 | 服务器本地磁盘（compose 卷 `/data/files`） | 几千笔/天规模，不引对象存储 |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Pinia | 国内管理后台事实标准，表格/表单组件齐全 |
| OpenAPI | drf-spectacular（OpenAPI 3，Swagger UI + ReDoc 两个在线入口） | 用户要求在线浏览；类型化 serializer 自动生成参数类型/枚举/取值范围 |
| 认证 | Django Session + 自定义用户表 + 两个角色（admin/operator）；SSO 用 django-allauth（OIDC client） | 内部系统 session 足够；OIDC 是用户要求的 SSO 方式，allauth 是最成熟的 Django OIDC 集成 |
| 前端构建部署 | Vite build → nginx 容器托管，`/api` 反代到 web | 前后端同域，实体机一台机全跑 |
| 金额单位 | 一律分（int64），展示层换算元 | 避免浮点误差 |
| 时区 | 服务器与数据库统一 Asia/Shanghai，时间存 UTC、展示转本地 | 对账日期按交易日本地日期切分 |

└──────────────────────────────────────┴──────────────────────────────────

## 6. 领域模型（核心字段）

配置域：
- **Channel 渠道**：code（wxpay/alipay/…）、名称、启用状态
- **FundAccount 资金账户**：所属渠道、名称、商户号、启用日期、启用余额（分）【启用日期+启用余额二期余额调节要用，必须建】、状态
- **BizType 业务类型**：code（PAY/REFUND/FEE/…）、名称、分组（收款/退款/费用）
- **ParseRule 解析规则**：目标表（payment/clearing/settlement）、文件格式（xlsx/csv/txt）、分隔符、表头行号、**列映射**（文件列名→标准字段，JSON）、**条件组**（JSON，用于筛选/费用项归集）、金额取值（JSON）
- **ReconcileProject 对账项目**：名称、类型（TRANSACTION/FUND/BALANCE）、A 方数据源+筛选条件、B 方数据源+筛选条件、**匹配键字段**、启用日期、最后对账日期、执行时间、频次（日）、告警接收人、状态
- **DisputeType 差错处理类型**：分组（交易/资金）、名称（如：补单/忽略-时间差/确认损失/资金人工转入确认/向渠道追款…）、SOP 说明文本【可配置，执行处理时选类型=选 SOP】

数据域：
- **InFile 上传文件**：所属获取任务、文件名、存储路径、大小、上传人、解析状态（pending/parsed/failed）、总行数、失败行数、失败原因
- **FetchTask 获取任务**：名称、侧（platform/channel）、渠道?、资金账户?、关联解析规则、方式（一期固定 manual_upload）【一期"上传槽位"，三期扩展为 api/sftp/sql】
- **PaymentData 自有支付**：商户订单号、支付单号、渠道、资金账户、业务类型、金额（分）、状态（SUCCESS/FAIL/CLOSED…）、交易时间、**对账日期**、来源文件?
- **ClearingData 渠道清算**：渠道单号、商户订单号、渠道、资金账户、业务类型、金额（分）、状态、交易时间、对账日期、来源文件
- **SettlementData 渠道结算**（二期资金对账用，一期先建表）：渠道、资金账户、款项/费用项、金额（分）、手续费（分）、实收（分）、结算日期、来源文件
- **ReconcileRun 对账批次**：项目、对账日期、状态（PENDING/RUNNING/SUCCESS/FAILED）、A 笔数、B 笔数、对平/单边A/单边B/错账数、开始/结束时间、触发方式（auto/manual/rerun）；**唯一 (项目, 对账日期)**
- **ReconcileResult 对账结果**（独立存储，每行源数据一条）：run、项目、对账日期、状态（MATCH/ONE_A/ONE_B/WRONG）、a_id?、b_id?、匹配键、差异金额（分）、业务类型；**部分唯一索引 (a_id, 项目) 与 (b_id, 项目)**——重对先删旧结果再写。结果行是"可再生的"，不承载生命周期
- **Dispute 差异记录**（差异的生命周期载体，**重对安全**）：项目、对账日期、类型（ONE_A/ONE_B/WRONG）、**a_id?/b_id?（引用源数据而非结果行）**、业务类型、金额、状态（OPEN/PROCESSING/CLOSED）、差错处理类型?、处理人、处理时间、备注、"历史已处理"标记、二期扩展：挂账凭证号、核销金额；**唯一 (项目, 对账日期, a_id) / (项目, 对账日期, b_id)**。重对时：已 CLOSED 的差异保留原记录（源数据仍在，引用不断）并标记"历史已处理"，只重生成 OPEN 的——因此已处理过的差异永远不会因重对丢引用或重复生成
- **HandleLog 处理记录**：dispute、动作（登记/处理/核销/重开）、操作人、时间、前后状态、备注【差错全程留痕】
- **Balance 余额**（二期）：账户、日期、系统余额、渠道余额、在途金额、未达账、调节后是否一致
- **WriteOff 核销**（二期）：dispute、核销类型、金额、操作人、时间

## 7. 对账引擎（一期交易对账）

**控制规则（钉死，来自文章"对账控制"）**
1. **连续性**：项目 P 对账日 D 可执行的前提：D ≥ 启用日期，且 D=启用日期 或 (P, D-1) 的 run 为 SUCCESS。不满足则拒绝执行并提示。
2. **状态**：(P, D) 唯一 run；已 SUCCESS 的日默认拒绝再执行，仅"重对"显式触发（**重对跳过连续性检查**，但要求 D-1 存在 run，缺失仅警告不阻断）；RUNNING 中的日拒绝一切新触发。
3. **并发保护**：创建/抢占 run 用 `select_for_update` + 唯一约束双保险；同一 (P, D) 并发触发只允许一个成功，其余返回"已在执行"。
4. **时间边界**：对账日期 = 交易时间的本地日期（A、B 各方用自己的时间字段，字段名在项目配置中指定）。
5. **任务流**：run 失败必须落状态+原因，触发告警（站内+邮件），人工可重跑。

**执行流程（Celery 任务 `run_reconcile(project_id, date, rerun=False)`）**
1. 校验控制规则 → 创建/抢占 run（RUNNING）
2. 按 A 方筛选条件取 PaymentData（对账日期=D），按 B 方条件取 ClearingData（对账日期=D）
3. B 方按匹配键（默认商户订单号，可配置）建内存索引
4. 逐行 A：无 B → ONE_A；B 唯一 → **状态规则**判定：A.status ∈ 项目配置的 A 方期望状态集 且 B.status ∈ B 方期望状态集，且金额相等（分）→ MATCH，否则 WRONG（记录差异金额，差异含金额差与状态不符两个维度）；B 同键多行 → 若项目开了"B 方汇总"，B 金额求和后同规则比（1v1 汇总模式）【状态集默认值：A 方 {SUCCESS}，B 方 {成功}，值映射在解析层归一后比较】
5. B 中未匹配到的剩余行 → ONE_B
6. 结果按 1000 行/批 bulk 写入（重对场景：先删该 (P, D) 旧结果，同一事务内重写）；更新 run 计数 → SUCCESS
7. 差异（非 MATCH）生成 Dispute(OPEN)；已 SUCCESS 过的项目重对时，已处理 Dispute 保留并标记"历史已处理"，不重复生成
8. 完成回调：更新项目最后对账日期；有差异则告警

**规模匹配**：几千笔/天，B 方全量入内存无压力；分块批量写避免大事务。多项目并行 = 多 worker 各跑各的（项目间无共享写热点，热点仅在 run 抢占）。

## 8. 差错处理（一期）

- 差异列表页：按项目/日期/类型/状态筛选，展示 A、B 两方关键字段并排 + 差异金额
- 处理动作：选择**差错处理类型**（从 DisputeType 配置选，如"补单""忽略-时间差""确认损失"）+ 必填备注 → Dispute 转 CLOSED，写 HandleLog
- 一期不做：长短款挂账凭证、核销金额、双向核销（二期）、账务推送（三期）
- 内置初始 DisputeType【决定】：补单、忽略-时间差、确认损失、人工核实后忽略（交易组）；资金组留二期

## 9. 文件接入与解析

- 上传：按"获取任务"入口上传（指明这是哪个渠道/账户、A 方还是 B 方的文件），multipart，单文件上限【决定】50MB
- 解析 = Celery 任务：按 ParseRule 读文件 → 逐行映射标准字段 → **整批校验，全部通过才入库**（回滚语义）；失败记录到行的错误清单（最多显示前 100 行）
- 列映射规则：文件列名（可空=忽略）→ 标准字段（金额/时间/状态/单号/业务类型…）；状态、业务类型支持值映射表（如文件里"成功"→SUCCESS）；金额字段带**进制乘数**（默认 ×100 元→分）；时间字段带 **strptime 格式**【决定：以上均存 ParseRule JSON，界面可编辑】
- 同一文件重复上传：同名同任务同日 → 拒绝（防重复入库）；显式"覆盖重传"可删旧数据再解析【决定】
- 内置默认解析模板【决定，用户可在界面改】：微信支付清算文件、支付宝结算文件、自有支付导出（订单号/支付单号/渠道/账户/业务类型/金额(元)/状态/时间 8 列，金额元→分转换）

## 10. 前端页面（一期）

1. **登录**（session，admin/operator 两角色，初始账号 admin/Admin@123 首登强制改密【决定】；启用 SSO 时增加「SSO 登录」按钮 → 跳转 IdP，回跳后自动进入；本地账号输入始终保留用于 admin 兜底）
2. **工作台**：今日各项目对账状态卡（未对/进行中/完成+差异数）、待处理差异数、最近失败任务
3. **对账项目管理**：列表 + 新增 + 设置（类型、A/B 方数据源与筛选条件、匹配键、B 方汇总开关、执行时间、告警接收人）
4. **基础配置**：渠道、资金账户、业务类型、解析规则（列映射编辑器）、获取任务、差错处理类型（六个 tab 页）
5. **数据管理**：文件上传（按获取任务）、上传/解析记录（状态、行数、失败原因、失败行明细）、源数据查询（Payment/Clearing/Settlement，按日期/单号/状态筛选，分页）
6. **对账结果**：项目 × 日期总览表（总笔数/对平/单边A/单边B/错账/已处理/待处理，行可展开明细）+ 明细页（A/B 并排、状态徽标、差异金额）+ 单项目"执行对账/重对"按钮
7. **差错处理**：差异列表 + 处理弹窗（选类型+备注）+ 处理记录时间线
8. **对账运行**：run 列表（项目/日期/状态/触发方式/起止时间/计数），失败可重跑
9. **系统管理**（仅 admin）：用户管理、角色；API 文档入口（/api/docs/ 外链）

路由守卫按角色：operator 无"系统管理"与"基础配置-解析规则"的写权限【决定】。

**API 文档（用户要求）**：后端挂载 OpenAPI 3 在线文档——`/api/docs/`（Swagger UI，可试调）+ `/api/redoc/`（只读浏览）+ `/api/schema`（JSON）。**全局约定：每个端点必须有类型化 schema**——状态/类型类参数用 Choice 枚举、金额用 int64（分）+ 说明、日期用 ISO 格式、查询参数用 `@extend_schema` 显式声明（名称/类型/取值/描述）、分页统一 PageResponse。新增端点不带完整 schema 视为不合格。

## 11. API 概要（/api/v1，DRF）

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| 渠道文件格式各家差异大（文章：Excel/TXT/XML/CSV/PDF） | 解析规则全配置化；内置模板只是默认值，界面可改；一期只承诺 xlsx/csv/txt |
| 启用余额记错导致余额调节全线偏差（文章强调 100% 准确） | 资金账户启用余额字段必填 + 修改需二次确认 + 修改留痕（二期前就把字段建对） |
| 实体机网络受限拉不到 docker 镜像 | 部署文档提供镜像导出/导入（docker save/load）离线安装步骤 |
| 重对误操作覆盖已处理差异 | 重对仅重生成未处理差异，已处理保留标记；操作留痕可审计 |
